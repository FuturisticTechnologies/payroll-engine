# Data dictionary — tenant-scoped tables

Owner: Data Analyst. Generated by reading `backend/app/models/` at M2 and kept
current by hand. `docs/03-data-model.md` is the signed-off design; this page is
the column-level reference engineers actually look things up in.

## 1. Tenancy rule

Every table below falls into exactly one of three categories. Knowing which one
a table is in tells you whether it needs a `tenant_id`, whether row-level
security applies, and whether a cross-tenant read is a bug or expected.

| Category | Tables | `tenant_id` | RLS |
|---|---|---|---|
| **Global catalog** | `roles`, `permissions`, `role_permissions` | No | No |
| **Identity** | `users` | No | No |
| **Tenant-scoped** | `tenants`, `employees`, `employment_contracts`, `user_tenant_roles`, `audit_logs`, `idempotency_keys` | Yes | Yes |

`users` is deliberately global: one person may be a payroll administrator for
more than one employer. The tenant relationship lives in `user_tenant_roles`,
not on the user, which is why revoking access is a row delete rather than an
account change.

## 2. Shared column conventions

| Column | Type | Source |
|---|---|---|
| `id` | `uuid` PK | `UUIDPkMixin` — generated application-side |
| `created_at` | `timestamptz` | `TimestampMixin` |
| `updated_at` | `timestamptz` | `TimestampMixin` |

UUID primary keys rather than sequences: pay run identifiers appear in URLs and
in HMRC correspondence, and a sequential integer leaks how many employees or
pay runs a competitor tenant has.

## 3. Tables

### `tenants` — the employer

| Column | Type | Null | Notes |
|---|---|---|---|
| `name` | `varchar(200)` | No | Trading name |
| `legal_name` | `varchar(255)` | No | As registered at Companies House |
| `slug` | `varchar(80)` | No | Unique, indexed. URL-safe key |
| `company_registration_number` | `varchar(*)` | Yes | Not all employers are companies |
| `paye_reference` | `varchar(32)` | Yes | HMRC PAYE scheme reference |
| `accounts_office_reference` | `varchar(*)` | Yes | Required before RTI in M6 |
| `default_pay_frequency` | `varchar` | No | Default for new contracts |
| `status` | `varchar(20)` | No | `active` on creation |

The two HMRC references are nullable because a tenant is created during
onboarding, before those values are known. They become mandatory at the point
of RTI submission, which is enforced in M6 rather than by the schema.

### `employees` — the individual

| Column | Type | Null | Notes |
|---|---|---|---|
| `tenant_id` | `uuid` | No | FK, RLS predicate |
| `employee_number` | `varchar(40)` | No | Unique per tenant, not globally |
| `first_name` / `last_name` | `varchar(100)` | No | |
| `email` | `varchar(255)` | No | Indexed |
| `national_insurance_number` | `varchar(*)` | No | **Special category adjacent — see §4** |
| `tax_code` | `varchar(10)` | No | Defaults `1257L`; authoritative history arrives in M4 |
| `ni_category` | `varchar(1)` | No | Defaults `A`; full catalog in M5 |
| `employment_start_date` | `date` | No | |
| `employment_status` | `varchar` | No | |
| `job_title` | `varchar(150)` | Yes | |

`employee_number` is unique *per tenant*. Employers arrive with their own
numbering and two of them will both have an employee `001`.

### `employment_contracts` — effective-dated terms

| Column | Type | Null | Notes |
|---|---|---|---|
| `tenant_id` / `employee_id` | `uuid` | No | FKs |
| `contract_type` | `varchar` | No | From the framework catalog |
| `pay_frequency` | `varchar` | No | weekly / fortnightly / four-weekly / monthly |
| `annual_salary` | `numeric` | Yes | **`Decimal`, never float** |
| `weekly_hours` | `numeric(5,2)` | Yes | |
| `effective_from` | `date` | No | |
| `effective_to` | `date` | Yes | `NULL` = currently in force |
| `currency` | `varchar(3)` | No | `GBP` |
| `is_primary` | `bool` | No | |

Terms are never updated in place. A pay rise is a new row with a new
`effective_from` and the previous row closed with an `effective_to`. This is
what makes it possible to recalculate a historic pay run and get the same
answer — the reason the evidence story works at all.

### `user_tenant_roles` — the access grant

| Column | Type | Null |
|---|---|---|
| `user_id` / `tenant_id` / `role_id` | `uuid` | No |
| `is_active` | `bool` | No |

The join that makes a user a member of an employer. Deactivating rather than
deleting keeps the audit trail intact.

### `audit_logs` — append-only

| Column | Type | Null | Notes |
|---|---|---|---|
| `occurred_at` | `timestamptz` | No | |
| `actor_user_id` | `uuid` | Yes | `NULL` for system actions |
| `actor_ip` | `varchar(45)` | Yes | IPv6-sized |
| `event_type` | `varchar(100)` | No | Indexed |
| `entity_type` / `entity_id` | `varchar(100)` | No | Indexed |
| `payload` | `json` | No | Passed through the log redaction helper |

No `updated_at`, deliberately: there is no code path that updates an audit row.

### `idempotency_keys` — replay protection

| Column | Type | Notes |
|---|---|---|
| `key` | `varchar(128)` | Client-supplied `Idempotency-Key` |
| `method` / `path` | `varchar` | Scope, so a key cannot cross endpoints |
| `request_hash` | `varchar(64)` | SHA-256 of the body |
| `status_code` / `response_body` | | The stored replay |
| `expires_at` | `timestamptz` | Nullable; sweep target |

`request_hash` is what makes the guarantee real. A repeated key with a
*different* body is a client bug and is rejected, rather than silently
returning the first response.

## 4. Data protection

| Column | Classification | Handling |
|---|---|---|
| `employees.national_insurance_number` | Personal, high-risk | Masked in logs by `app.core.redaction`; never in a URL |
| `employees.email`, `users.email` | Personal | Masked in logs, domain retained |
| `users.hashed_password` | Credential | Argon2/bcrypt hash; never logged or returned |
| `audit_logs.payload` | Mixed | Redacted before write |
| Salary and pay figures | Personal, confidential | Tenant-scoped, RLS-enforced |

Retention is 7 years for anything forming part of the payroll record — the
audit log and the ledger. Operational logs are not part of that record and are
retained for 90 days, which is why identifiers are masked rather than stored
and purged.
